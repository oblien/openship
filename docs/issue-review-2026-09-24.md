## Follow-up: deployment completion and installation reports

Baseline: main at `960910ca`. Branch: `fix/deployment-auth-issues-20260924`.

The #919 follow-up repairs worker completion in the shared engine. The outer worker retains ownership until its idempotent database acknowledgement succeeds, with sequential retries backing off from one second to a maximum thirty-second interval. Cancellation polling stops after host work has returned; retries do not repeat image preparation, deployment or cleanup. The native engine's drain still waits for durable completion. No lease is expired based on its age, so a slow live worker cannot race a replacement deployment.

The counter review found additional defects. Cancellation now records the deployment outcome and build-session duration in one database transaction, while leaving `finishedAt` to the worker acknowledgement. Late worker results cannot reset that duration or undo cancellation, but can still persist their cleanup logs. The handler reads the execution lease after winning cancellation, so a racing kickoff cannot make both the handler and worker own cleanup. Other terminal lifecycle hooks record their measured duration with the deployment outcome, preserving a timing source when the later session/log write fails. The shared status projection honors durable terminal outcomes over stale in-memory phases.

Both dashboard build views now use the same timestamp-based clock for one deployment attempt. Terminal events freeze the displayed duration and reconcile it with the persisted status; polling copies timing and cannot overlap requests. Missing historical terminal durations display as unknown instead of elapsed days. Refresh does not reintroduce “Stopping” after acknowledgement; retries do not carry previous attempts or rewrite the old result when admission fails. Late requests from an older deployment view cannot replace the current status or clock.

A page opened while the build is still queued also fetches its eventual start timestamp after the stream connects. The poll stops once that timestamp is known and the stream is healthy. Its regression initially remained at an unknown duration after the worker started, then passed with this correction.
