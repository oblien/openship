title: Your first deployment
description: Review a new project's configuration, verify the release, and prepare the next deployment.

**Before you start:** open an OpenShip dashboard, identify your source repository or folder, and choose
where the application should run. Use the [quickstart](/docs/getting-started/quickstart) if you need to set up OpenShip first.

## The walkthrough

<Steps>
<Step>

### Open a new project

Select **New Project** to open the Library. Choose GitHub, a repository URL, a local folder, or a template.
For a private repository, configure [source access](/docs/guides/git-authentication) first.

</Step>
<Step>

### Pick the repository you want

Choose the repository and branch. For a monorepo, check the working directory so OpenShip builds the intended
application. For Compose, check the Compose file path and detected services.

The [GitHub guide](/docs/guides/deploy-from-github) covers repository selection and push-triggered deployments.

</Step>
<Step>

### Choose where it should run (you might not see this)

Select a connected server, a Cloud space with sufficient capacity, or an available local runtime.
The wizard may reuse an existing selection. Check the destination in the summary before deploying.

Changing the destination later may require moving persistent data and updating DNS.

</Step>
<Step>

### Read the setup screen

| Check | What to verify |
| --- | --- |
| Source | Repository, branch, working directory, and Compose path where relevant. |
| Build | Framework, install/build commands, Dockerfile, and output directory. |
| Runtime | Start command and listening port. Use `0.0.0.0` when the runtime requires external container access. |
| Environment | Required secrets and URLs; distinguish build inputs from runtime overrides. |
| Services | Which services are public, their dependencies, and persistent volumes. |
| Destination | Selected server or Cloud space, capacity, and configured domain. |

Review the detected values against your application, then select **Deploy**.

</Step>
<Step>

### Watch it go live

Follow the deployment log. If a stage fails, inspect the failing command and surrounding output before
retrying. A successful build alone does not verify runtime behavior.

<DocsScreenshot name="build" alt="A deployment in the Build stage, showing progress and the build terminal." caption="Follow the build log to see the current stage and command output. Select the image to open it at full size." />

</Step>
</Steps>

## What "live" looks like

<DocsScreenshot name="ship" alt="A completed deployment with Ready status and the Open site action." caption="A ready deployment shows the release status and a link to your application." />

After the deployment reports ready:

1. Open the assigned route and check an actual page or API response.
2. Read runtime logs for startup, connection, or permission errors.
3. Test an application operation that reaches the database or other dependencies.
4. Confirm the domain and HTTPS certificate if the service is public.

Add a [custom domain](/docs/guides/custom-domains) when ready. For production, complete the
[production checklist](/docs/guides/production-readiness) before sending customer traffic.

## Troubleshooting

| Failure | Investigate |
| --- | --- |
| Missing repository | GitHub App installation and repository permissions. |
| Failed build | Build command, working directory, dependency versions, and build-time values. |
| Runtime exits or route returns an error | Start command, port, runtime environment, service health, and networking. |
| Data disappears after redeployment | Persistent volume or external storage configuration. |

See [deployment troubleshooting](/docs/troubleshooting/deployments) for specific errors.
