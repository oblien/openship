Domains connect hostnames to a project and track DNS verification and TLS certificates. The SDK takes a
project ID as the first argument when creating or listing domains; REST includes it in the body or query.

## Set a domain HTTP body limit

Self-hosted nginx/OpenResty domains can override the project's request-body limit independently:

```ts
await ship.domains.update("dom_api", { proxy: { clientMaxBodySize: "2m" } });
await ship.domains.update("dom_polling", { proxy: { clientMaxBodySize: "1m" } });
// Clear the override and inherit the project again.
await ship.domains.update("dom_polling", { proxy: null });
```

The REST endpoint is `PATCH /api/domains/:id`. It requires write access to the domain's project.

| Request body | Result |
| --- | --- |
| `{}` | Leave the saved override unchanged. |
| `{"proxy":null}` | Clear the override and inherit the project. |
| `{"proxy":{}}` | Replace the override with an empty object, also inheriting the project. |
| `{"proxy":{"clientMaxBodySize":"2m"}}` | Replace the override with a 2 MiB cap. |
| `{"proxy":{"clientMaxBodySize":"0"}}` | Disable the HTTP body limit for this domain. |

Use a positive integer with a lowercase `k`, `m`, or `g` suffix, or `0` for unlimited.
Units are binary: one `m` is 1,048,576 bytes. Expanded sizes must fit JavaScript's
safe integer byte range.
Bare nonzero numbers, unknown fields, unsafe values, and numeric overflow are rejected.
New overrides require the selected routing provider to support domain body limits; detecting an
unrelated nginx installation is not sufficient. Unsupported providers return
`CAPABILITY_UNAVAILABLE` before saving a new override; an unreachable or unconfirmed
active edge returns `EDGE_UNAVAILABLE`. Clearing a legacy override with `null` or `{}` restores inheritance
even when the provider cannot enforce an override; a successful save alone is not application proof.
Projects with explicit domain overrides cannot transfer to Cloud or bind to a cluster;
those transitions fail with `DOMAIN_PROXY_SETTINGS_UNSUPPORTED` before changing the target.
Clear the overrides before moving to either destination.

The domain override takes precedence over the project, then the installed Edge HTTP default.
The standard Edge default is `50m`; read-back reports an unobserved inherited default as unknown.
Inheritance does not store or render a copy of that Edge default. Later project changes
affect inheriting domains only; other project proxy settings still apply to every domain.
There is no service-level or path-level body-limit override.
This limits incoming HTTP request bodies, including chunked uploads and Socket.IO polling POSTs.
It does not limit response sizes or throughput, set WebSocket frame/message limits, or raise
the application's own upload limit. Existing rate rules and their path selection remain independent.

For a running, deployed project, saving re-applies the current routing without a rebuild.
A known-supported provider can also save desired settings before the first deployment or while
paused. Those changes remain pending until deployment or explicit resume; saving does not scan
the live Edge, resume the project, or recreate paused routes. Read-back remains unobservable
before deployment: `observed` and `configurationMatches` are null. An unobserved inherited Edge default also
has a null `effective` value.

If apply fails, the endpoint returns
`DOMAIN_PROXY_APPLY_FAILED` and keeps the desired setting for retry. Repeat the update or use
**Retry routing** in the dashboard. Config validation or reload failure restores the previous
vhost and stored route sidecar. Redeploys, routing retries, certificate activation, and stored-route
repair retain the resolved cap. A failed apply retains its project routing warning across
navigation. A successful repeat save resolves this operation's warning while preserving unrelated
warnings. Existing hostnames keep their managed Cloud registrations during a cap-only edit.
Read `GET /api/projects/:id/edge-config` afterward:
`hosts[].bodyLimit` reports `saved`, `effective`, `source`, `observed`, and `configurationMatches` for each hostname.
`configurationMatches` compares the generated server-block file with the resolved cap; `null` means it could not be compared.
A matching file does not prove the running workers use that value, and neither does a saved value, so the API does not report whether the running workers use it.
When a domain has an explicit override, its observed body limit is excluded from the project-level
`adoptable` settings, so adopting configuration drift cannot change the default for inheriting siblings.

For command syntax, see [`openship domain update`](/docs/cli/reference/domain#openship-domain-update).

## Preview required DNS

Side-effect-free: pass a hostname, get back the records to create. `POST` is used only so the hostname
travels in the body.

<Tabs items={['SDK', 'REST API']} groupId="api-transport" persist>
<Tab value="SDK">

```ts
const result = await ship.domains.preview({
  hostname: "app.example.com",
});
console.log(result);
```

</Tab>
<Tab value="REST API">

```bash
curl -X POST "$OPENSHIP_URL/api/domains/preview" \
  -H "Authorization: Bearer $OPENSHIP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"hostname":"app.example.com"}'
```

</Tab>
</Tabs>

The response's `mode` tells you which setup applies: `selfhosted` (an A record to your server), `cloud`
(a CNAME to Openship Cloud), or `external` (a TXT record only — you front TLS yourself).

Once DNS is in place, verify it. Openship Cloud checks its routing and ownership records. Self-hosted
verification obtains or reuses the certificate on the deployment server. Domains with external ingress
keep TLS at their upstream proxy.

## Wildcard HTTPS and manual TXT

Wildcard and DNS-01 domains on self-hosted targets use the same operations in the dashboard, SDK and MCP.
Deploy and enable the project first. An external ingress or uploaded certificate keeps its existing TLS flow.

```ts
// "automatic" uses a connected DNS provider. "manual" generates a real ACME TXT.
const attempt = await ship.domains.startDnsChallenge("dom_123", { mode: "manual" });
const current = await ship.domains.dnsChallenge("dom_123");
// Once current.status is "waiting", publish current.record at the DNS provider.
// Then explicitly ask Openship to check it:
await ship.domains.checkDnsChallenge("dom_123", { attemptId: attempt.id });
```

Start and check return **202** with `{ data: attempt }`; they do not hold the HTTP request open for
certificate issuance. Read `GET /api/domains/:id/dns/challenge` until the result settles. It returns
`{ data: null }` before any attempt. The safe attempt includes `id`, `domainId`, `mode`, `status`,
`record`, `expiresAt`, `logs`, `error`, `createdAt` and `updatedAt`. It never includes private keys,
account credentials or serialized ACME orders.

`preparing`, `checking`, `installing` and `cancelling` represent running work. `waiting` needs the operator's
TXT; stop polling until they act. `completed`, `failed`, `cancelled` and `expired` are settled results.
A missing TXT or retryable validation/install error keeps the same order in `waiting` with its error.
Repeated starts reuse an active attempt; check and cancel require its current `attemptId` and reject
a stale ID with **409**. An installation that has already started cannot be cancelled.

Manual renewal uses `startDnsChallenge(id, { mode: "manual", force: true })` and a fresh TXT value.
`cancelDnsChallenge(id, { attemptId })` discards an unfinished manual attempt without removing existing TLS.
Connected-provider mode renews automatically when the SSL job is enabled. See the
[wildcard guide](/docs/guides/custom-domains#wildcard-domains) for DNS names, record cleanup and renewal steps.

## Access

A project grant covers its domains: `read` for the `domain:read` routes, `write` for `domain:write`, and
`admin` for `DELETE /api/domains/:id` (`domain:admin`). A token can instead hold the capabilities
`domains:read`, `domains:write` and `domains:delete` on the project, which reach the same routes and nothing
else on the project. See [Capabilities](/docs/security/permissions#capabilities-finer-than-read--write--admin).

## Errors

<Callout title="422 — verification failed" type="warn">
The DNS records aren't resolving yet, or don't match. DNS can take minutes to hours to propagate. Confirm
the records match `preview` exactly, then retry. The response's `cnameVerified` / `txtVerified` flags tell
you which check is still failing.
</Callout>

<Callout title="404 on a per-domain route" type="error">
The `:id` doesn't belong to your organization (or was deleted). List your domains with `GET /api/domains`
to get valid IDs.
</Callout>
