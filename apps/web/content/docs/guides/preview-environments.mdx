Deploy a branch into a separate project environment with its own deployment state and URL. Use preview
configuration and separate data dependencies where isolation is required; shared databases and external
services remain shared unless you configure them otherwise.

<Callout title="What you need first">
- A project that's already set up in Openship (see [Deploy from GitHub](/docs/guides/deploy-from-github) if you don't have one yet).
- The project connected to **GitHub**, with more than one branch — an environment is built from a branch.
- A branch to point it at (for example a `staging` or `preview` branch).
</Callout>

## What "production" and "preview" mean

- **Production** serves your live application and usually follows `main` or `master`.
- **Preview** runs a different branch at a separate URL, with its own variables and deployment history.
  Use separate databases and external services to keep preview writes away from production data.

Openship decides which type a new environment is by looking at its branch:

- A branch named `main` or `master` becomes a **production** environment.
- Any other branch becomes a **preview** environment.
- If you create one by hand without a branch, it's a **development** environment.

Each environment has its own project ID, address, variables, and deployment history. When you create one,
OpenShip copies the source project's framework, build commands, and settings. This does not copy a
database or isolate external dependencies referenced by that configuration.

## Automatic pull request previews

Open the source environment's **Git → Pull request previews**, then enable previews.
This applies to every supported Git-backed stack, including monorepos and Compose services.
Open, non-draft pull requests from the same repository targeting this environment's branch
get an isolated environment. Fork pull requests are excluded. Existing open pull requests
are discovered when you enable the setting.

Set project and service variables in **Environment → Preview** before enabling automation.
Only those values are copied into the new environment's own production variable set;
production variables and inline service secrets are not copied. Preview values are refreshed
on each new commit. Move variables out of install, build, start and lifecycle commands first.

Each environment inherits its source's build configuration when created, uses fresh named
volumes, and gets a distinct URL for each public service port. Workers do not get a public URL.
On a server, supply a **Preview base domain** such as `preview.example.com` and point its
wildcard DNS record at that server. HTTPS verification must succeed before deployment.
Leave the field empty to use managed domains when the deployment target supports them.

New commits deploy their exact SHA. Openship publishes deployment checks through the existing
GitHub Checks integration and can maintain one comment with the preview URL and deployment
link. The GitHub identity needs permission to read pull requests; comments also need write
access. Existing GitHub App installations may need to accept updated permissions.

Closing or merging a pull request, converting it to a draft, changing its base away from the
source branch, or disabling previews removes its environment and owned volumes. Cleanup retries
when the server is unavailable. Reopening an eligible pull request creates a fresh environment.
Delivery deduplication, leases, and periodic reconciliation recover missed webhooks and restarts.
Failures and pending cleanup are visible in the source environment's preview list.

Whole-instance transfers preserve preview ownership and pending cleanup. Disable previews and wait
for cleanup before transferring their environments individually. Portable configuration exports
clear preview automation and host-specific cache receipts; configure them on the destination.

Automation currently supports Docker, direct-server and managed Cloud targets. Cluster targets,
host bind mounts, shared host/container namespaces, and generated service files or inline Dockerfiles
require a separate preview template and are rejected during setup. They cannot silently reuse
production infrastructure. Standard repository Dockerfiles and Compose files are supported.

## Create an environment from a branch

Use the **environment switcher** at the top of the project page.

<Steps>

<Step>

### Open the project and find the switcher

Open the project. Find the current environment name and branch, then select the **+** button beside them.

</Step>

<Step>

### Press + and pick a branch

Select a repository branch; use **Search branches** to filter the list. OpenShip creates the environment
and opens its project page. Its name is generated from the branch, such as `feature/new-home` →
**Feature New Home**.

</Step>

<Step>

### Deploy the new environment

Review the new environment's variables and data dependencies, then select **Deploy**. Creating a manual
environment does not deploy it automatically. Once deployed, verify its URL and runtime logs.

</Step>

</Steps>

### Switching between environments

Open the switcher and select an environment. Each row shows its name and branch; the selected environment
has a check mark. Deployments, logs, and variables belong to the environment you are viewing.

### Creating one by hand (no branch)

Select **Manual environment** in the Add-branch panel. Enter a name and, optionally, a **Branch label**,
then select **Create**. An environment without a branch is classified as **development**.

## CLI

Select the environment's project ID with `--project`. The `--env` flag selects the deployment mode and
variable set; it does **not** create a separate environment. A preview deployment against a production
project is rejected.

```bash
# Deploy the project your folder is linked to, as production (this is the default)
openship deploy

# Deploy an existing non-production environment with preview variables
openship deploy --project <environment-project-id> --env preview
```

<Callout title="Only two values" type="info">
`--env` accepts exactly `production` or `preview`. Anything else is rejected. If you leave it off, it defaults
to `production`.
</Callout>

Add `--watch` to follow build progress:

```bash
openship deploy --project <environment-project-id> --env preview --watch
```

Verify the deployment URL and runtime logs after the build finishes.

## Troubleshooting

<Callout title="No branches show up when I press +" type="warn">
The environment list is built from your GitHub branches, so the project has to be connected to GitHub and have
branches to show. If the list is empty, check that the project is linked to a repository. See
[Deploy from GitHub](/docs/guides/deploy-from-github) for connecting GitHub.
</Callout>

<Callout title="“Branch … was not found”" type="error">
Openship couldn't find that branch in the repository. Make sure the branch actually exists on GitHub (and that
it's pushed, not just local), then try again.
</Callout>

<Callout title="An environment with that name already exists" type="warn">
Each environment under a project needs a unique name. If you already turned that branch into an environment,
switch to it from the pill instead of making a second.
</Callout>

<Callout title="My preview is missing a secret" type="warn">
Variables are per-environment — a preview copy doesn't automatically inherit production's. Open the preview
environment and add what it needs. See [Environment variables](/docs/guides/environment-variables).
</Callout>
